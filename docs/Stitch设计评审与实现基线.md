# Stitch 设计评审与前端实现基线

- 版本：1.0
- 日期：2026-09-23
- 设计来源：`design/stitch-export/stitch_stitch_design_system/`
- 需求依据：[PRD v1.0](./PRD.md)
- 页面依据：[Stitch 前端页面设计说明](./Stitch前端页面设计说明.md)
- 用途：规定哪些 Stitch 设计进入正式前端，哪些仅作视觉参考，哪些不实现

## 1. 评审结论

本次 Stitch 导出包含 26 张页面或状态设计、对应静态 HTML，以及一份 `DESIGN.md` 设计系统。整体视觉方向符合产品定位，可以作为正式前端的主要视觉参考；页面代码仅作为结构参考，不直接作为生产代码使用。

正式实现遵循以下优先级：

1. 已审核的 PRD 决定功能范围、角色权限和验收标准。
2. 技术设计决定数据状态、关键链路和安全边界。
3. 《Stitch 前端页面设计说明》决定页面应覆盖的状态和交互。
4. Stitch 截图决定视觉表现和局部布局。
5. Stitch `code.html` 仅用于提取颜色、尺寸、间距和组件结构。

当 Stitch 设计与前三项冲突时，不采纳冲突部分。

## 2. 采纳的设计系统

以下内容直接作为正式前端的设计基线：

- 浅灰画布、白色内容面板和蓝色主操作色。
- 224px 桌面侧边栏、56～64px 顶栏和 8px 间距体系。
- `#2563EB` 主色、`#F7F8FA` 页面背景、`#E5E7EB` 边框。
- 中文系统无衬线字体；SQL、DSL、任务编号使用等宽字体。
- 轻边框、弱阴影、中等圆角、高信息密度的企业后台风格。
- 成功、警告、失败、运行中、停止状态同时使用颜色、图标和文字。
- 表格、筛选栏、表单、步骤条、抽屉、确认框、任务时间线的整体视觉语言。
- 智能问答的会话栏、对话主区、执行过程栏和证据抽屉布局。
- 登录、首次改密、模型管理、数据源管理、知识库和账号管理的主要页面结构。

## 3. 需要简化后采纳的设计

### 3.1 全局应用外壳

保留导航、顶栏、账号菜单和状态标签样式。删除下列装饰性或未定义信息：

- “KMS 隔离网关”“安全只读网络”“隔离区 A-04”。
- “API 与推理网关正常”“集群状态稳定”“推理引擎吞吐 99.8%”。
- 通知中心、帮助中心及其红点；除非后续 PRD 明确加入。
- 页面中的 `v2.4`、`v2.8.4`、`Enterprise Engine`、`Model Hub` 等虚构版本和英文产品名。

正式产品统一显示“智能分析平台”。顶栏只保留页面标题或面包屑、必要操作和当前账号菜单。

### 3.2 智能问答

`_1`、`_2`、`_3`、`_4` 的三栏结构、执行步骤、证据引用和异常状态具有较高参考价值，作为问答页面的主要设计来源。

需要调整：

- 将过多的安全审计术语改成普通业务用户能理解的状态文案。
- 不展示模型内部思维链，只展示输入确认、数据源选择、实际查询、检索证据和结果生成等可审计事实。
- 图表和数据表根据真实返回数据生成，不固化 Stitch 示例中的销售或运维指标。
- “前往统一运维工单系统”“下发配置”等动作不实现。
- 保留 SQL/DSL 查看和复制；不提供用户直接修改并执行任意 SQL/DSL 的入口。

### 3.3 模型管理

`_5` 和 `_6` 的列表、表单分区、测试结果和启停状态可以参考。

需要调整：

- 页面名称统一为“模型管理”，删除 `Model Hub v2.4`。
- 删除吞吐率、令牌速率、生产集群监控等第一版未定义指标。
- 测试只呈现连接、认证、模型可用性、工具调用/结构化输出能力和耗时。
- API Key 永不回显；编辑时使用保留、替换或清除语义。
- 对话模型与 Embedding 模型分开管理，不能混在一个模型类型筛选中。

### 3.4 数据源管理

`mysql_elasticsearch`、`mysql_1`、`mysql_2` 和 `elasticsearch_1`～`elasticsearch_4` 的步骤、字段配置、能力矩阵和发布检查可以参考。

需要调整：

- 删除“拓扑监控”“沙箱审计”“策略命中率”等未定义运营指标。
- MySQL 保留连接、只读验证、表字段授权、关系、业务口径和发布检查。
- Elasticsearch 保留单个具体索引、mapping、字段能力、UUID 变化和发布检查。
- 页面中的 CRITICAL RULE 等英文警示改成简洁中文。
- 不提供写入、授权变更、索引管理或其他会修改业务数据的操作。

### 3.5 知识库

`_8` 和 `_9` 的列表、文档状态、详情分区、版本及索引信息可以参考。

需要调整：

- 示例业务由运维故障库改为中性业务知识库数据。
- 精简过多统计卡和引用热度信息，优先展示文档处理与索引健康状态。
- 明确区分上传完成、解析完成、待建索引和可检索。
- 保留文档版本、失败重试、索引代次和旧索引继续在线的表达。
- 删除“在某运维会话中作为第一候选证据”等跨用户会话信息，避免权限误导。

### 3.6 账号和认证

`_10`、`_11`、`_12`、`_13` 的视觉方向可以参考。

需要调整：

- 登录页保留用户名、密码、错误提示和重试限制；不显示内部认证架构信息。
- 首次登录强制改密保留，但简化安全检查说明。
- 账号表格仅保留用户名、显示名称、角色、状态、首次改密状态、最近登录和操作。
- 角色只有普通用户和管理员，删除部门、工号、数据权限组合和自定义权限。
- 停用确认只说明登录影响，不虚构“重要安全事件同步至合规审计流”。
- 不提供管理员查看其他用户会话的入口。

### 3.7 系统状态页

`403` 和 `404` 保留整体版式，但删除网关可用率、Trace ID、资源 URI、认证模式等诊断信息。普通用户只需要知道发生了什么以及下一步可以做什么。

500 错误优先设计为简洁通用页和局部错误组件。详细请求编号可以保留，内部堆栈、服务地址、查询内容和认证信息不得展示。

## 4. 不纳入第一版的设计

以下设计不作为独立产品页面实现：

- `_7`：严重故障排查、QPS 与 HTTP 500 对齐分析及下发限流。
- `http_500_ip`：围绕特定 IP 的故障诊断页面。
- `ip_10.198.42.15_qps`：QPS 专项分析与网关限流动作。
- `ip_10.198.42.15_latency_ms_p95_p99`：延迟百分位专项排障页面。
- 任何“一键下发工单”“下发网关规则”“修改连接池”“通知商户”等外部运维操作。
- 独立监控大屏、系统拓扑、集群吞吐、审计中心和告警中心。

这些页面的图表、结论卡、证据列表可以作为“智能问答返回复杂分析结果”时的组件样式参考，但不会形成固定路由或专用业务模块。

## 5. 导出代码的使用原则

所有 `code.html` 都是独立静态页面，主要使用 Tailwind CDN、Google Fonts 和 Material Symbols。正式工程不能直接复制运行，原因包括：

- CDN 运行时 Tailwind 不适合作为正式构建方案。
- 多个页面重复定义颜色、字体、导航和组件，缺少统一维护入口。
- 页面中的按钮和链接大多没有真实路由、数据状态或接口行为。
- 部分页面使用大量绝对尺寸，对不同屏幕宽度的适配不足。
- Google Fonts 和 Material Symbols 依赖公网，内部部署环境可能无法访问。
- 示例中包含虚构生产信息、IP、账号、安全架构和运维动作。

正式实现应从 `DESIGN.md` 提取设计令牌，在前端工程中建立统一主题、应用外壳和组件库；图标采用随项目打包的依赖或本地资源；页面使用真实路由、权限守卫、接口状态和响应式规则。

## 7. 正式前端的首批页面范围

第一阶段应先建立统一工程和高复用骨架，再逐页接入业务：

1. 应用主题、图标、基础组件和响应式应用外壳。
2. 登录、首次改密、403、404 和通用异常反馈。
3. 智能问答页面及空闲、运行、成功、澄清、部分失败、失败、取消状态。
4. 模型与 Embedding 模型管理。
5. 数据源列表及 MySQL、Elasticsearch 配置流程。
6. 知识库列表、详情、上传和索引任务。
7. 账号管理和修改自己的密码。

正式编码开始前，需要在项目根目录建立前端工程。目前仓库只有技术验证模块，尚无可继续扩展的前端应用。
